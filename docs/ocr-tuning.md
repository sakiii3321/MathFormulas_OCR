# DeepSeek 公式 OCR 调优记录

记录日期：2026-11-18。本轮结论来自本机配置的 DeepSeek 官方接口，实际请求的模型别名为 `deepseek-flash`，接口为 `https://api.deepseek.com`。模型别名可能由服务端更新，因此本记录不把别名视为不可变的模型版本。

公式模式采用 **strict** 提示词。主测试中 LaTeX、MathML、OMML 均为 **148/156（94.9%）**，MathType 为 **143/156（91.7%）**。这是本组样例的通过率，不是对任意公式、截图质量或学科分布的随机抽样准确率。这些改进可从源码运行，已发布的 1.3 EXE 使用此前版本。

## 样本、请求和评分方法

主测试包含 108 个公开文献/数学资料回归样例，以及 48 个针对已发现问题设计的合成样例，共 156 个输入。另设字体专项：24 个字体样例，加上 M18、T25–T28 各 3 次重复，共 39 对 strict/serif 比较。全部实验共有 180 个不同输入，重复请求不冒充新增独立样本。

请求账本共 **550 次**：主测试 3 套提示词共 468 次，字体专项 78 次，网络超时补测 4 次。结果为 **546 次成功返回、4 次超时**；“成功返回”只说明请求完成，不代表识别正确。4 次超时发生于 serif 的 E07、E10、E11、E12；每例仅补测一次，首轮失败和补测分别保存，没有用补测覆盖原始结果。调优阶段使用了实验预算中的 **550/2000** 次。

API 只接收输入图像、对应提示词和识别请求；清单中的参考 LaTeX 用于本地对照，不发送给模型。保存原始返回、清洗后的 LaTeX、输入哈希、提示词哈希、错误和耗时，以区分识别、清洗和转换阶段。

验收采用 AI 逐例视觉复核，并保留可检查的图像和源码证据：

- LaTeX 实际编译并渲染，与输入图像比较。
- MathML 使用程序实际预览 HTML 和字体渲染，避免以测试页面的默认字体代替应用行为。
- OMML 在真实 Word 中创建公式，保存可编辑 DOCX，并经 Word 导出 PDF、转为 PNG；同时记录公式对象数量。
- MathType 输出先生成 WMF，再由真实 Word 导入、导出 PDF、转为 PNG。最终评分不使用 Pillow 对 WMF 的替代渲染。

“端到端通过”要求最终结果忠实于输入图像；“转换通过”只检查输出是否忠实于已经识别的 LaTeX。因此，模型识别错误可以导致所有格式端到端失败，而转换本身仍然通过。转换调用不报错、XML 可解析，也不等于视觉正确。

评分保留有意义的字体身份、上下标、重音、分式边界、运算符、矩阵元素和分组范围。合并原有分式等代数改写即使等价也判失败；等效 LaTeX 命令、合理换行和不改变分组的字号差异可通过。固定高度括号、对齐和间距等可读的排版差异单独记为警告。字体专项中，同式不同字体的符号身份必须保留。

这不是独立人工盲审，也不是未见样本上的泛化评估：样本包含回归用例和针对性构造，且用于提示词选择。通过率只描述本次环境、输入及判定规则下的结果。

## 提示词选择

| 方案 | 主测试通过 | 说明 |
| --- | ---: | --- |
| baseline | 145/156（92.9%） | 基础忠实转录要求 |
| strict | 148/156（94.9%） | 明确禁止化简和合并分式，区分点、重音、字体与结构；最终采用 |
| serif，首次请求 | 144/156（92.3%） | 增加衬线/无衬线检查；包括 4 次网络超时失败 |
| serif，允许每次超时补测一次 | 147/156（94.2%） | 原始结果保留；这是独立列出的补测策略结果 |

字体专项中，serif 将通过数从 **19/39（48.7%）提高到 30/39（76.9%）**。但它在主测试补测后仍低于 strict，并引入其他上下标、粗体身份和分式结构错误，因此没有全局启用。不能仅凭专项收益把字体提示应用到全部公式。

本地 `formula_ocr/prompts.py` 仅对已列出的 DeepSeek 官方 Flash 模型别名启用 strict；其他提供商和混合文档识别保持其各自提示。最终 156 例的提示词哈希与采用的生产提示一致，见实验 `summary.json`。

## 最终格式结果与剩余问题

| 输出格式 | 对原图的端到端通过 | 对识别 LaTeX 的转换通过 |
| --- | ---: | ---: |
| LaTeX | 148/156（94.9%） | 不适用 |
| MathML | 148/156（94.9%） | 156/156（100%） |
| OMML / Word 原生公式 | 148/156（94.9%） | 156/156（100%） |
| MathType | 143/156（91.7%） | 151/156（96.8%） |

四种输出均通过的样例为 **143/156**。MathML/OMML 的转换全通过只适用于本组样例，并不表示全部 LaTeX 功能或所有 Word 版本均受支持。

模型识别阶段剩余 **8 个失败**：

| 样例 | 问题 |
| --- | --- |
| M18 | Ferrers 函数的无衬线 `\mathsf{P}` 被识别为有衬线直立 `\mathrm{P}`，符号身份改变 |
| P06 | 左侧二阶时间导数的双点变成单点，导数阶数改变 |
| P10 | 求和项的普通 `Z` 被改成花体 `\mathcal{Z}`，与同式另一函数身份混淆 |
| P15 | 相邻两个分式 `(N²/2)(Ω/V)` 被合并为 `N²Ω/(2V)`，不再忠实转录原结构 |
| T25、T26 | 第一项无衬线 P 被识别为有衬线直立 P |
| T27、T28 | 第二项有衬线直立 P 被识别为无衬线 P |

MathType 额外存在 **5 个转换失败：M35、T33–T36**。上花括号或下花括号在真实 Word 渲染中变成黑菱形问号，标签仍在，但括号分组范围丢失。对应 LaTeX、MathML 和 OMML 正常，不能归因于模型识别，也不能以“导入没有异常”计为通过。

另有未造成语义丢失的排版限制：部分分段式花括号、求值竖线和范数竖线高度固定；嵌套多行环境可能变成左右排列；多行等号/赋值箭头的对齐与间距有差异；MathType 双点重音距离基字偏高。例如 E36 的范数范围及下标完整，但竖线高度、纵向位置和续行对齐仍与原图不同。这些均在逐例记录中标为 `layout_warning`，不等同于精确复刻排版。

本轮本地转换修复覆盖 MathML 结构规范化、点/横线及重音兼容、OMML 括线结构等问题；仍保留以上未解决项。记录的自动化验证命令为 `.venv/Scripts/python -m pytest tests -q`，结果 **268 项通过**，环境包括本机桌面 MathType。自动化测试与 156 例视觉验收是不同验证层次。

真实剪贴板烟测曾间歇出现 Word 的“剪贴板为空或无效”错误，同一公式在其他轮次能成功，失败后原数据仍完整。证据支持同步 COM 测试与 Qt/OLE 就绪时序问题，尚不能定位某个外部占用进程。仅给烟测增加有上限的就绪检查，未向产品复制逻辑加入固定延迟，也没有重试粘贴调用。随后诊断两轮 24/24、最终脚本 12/12 均通过，Word 为 16.0 / Build 16.0.19127。原始失败和后续记录保存在 `clipboard-investigation/`；这 36 次是三条公式的重复工程检查，不计入上述 156 例通过率。

## 100 个新公式的独立验证

固定提示词后，从 NIST 数学函数数字图书馆预选的 44 节中建立候选集，与既有 180 个输入去重。用种子 `20261118` 从 649 个候选中无放回抽取 100 个公式，覆盖 27 章。每张出版方原图只请求一次，100 次均返回，逐例核对原图和四种渲染结果。

| 输出格式 | 忠实于原图 | 忠实于识别的 LaTeX |
| --- | ---: | ---: |
| LaTeX | 94/100 | — |
| MathML | 93/100 | 99/100 |
| Word OMML | 93/100 | 99/100 |
| MathType | 92/100 | 98/100 |

六例识别错误涉及两处主值积分、两处有数学含义的字体、一处下取整符号和一处根号范围。另有一例的连续导数撇号在三种转换中变为嵌套上标，一例的水平长箭头在 MathType 中显示为缺字符号。四种输出同时通过 92 例。结果描述本次抽取的印刷数学公式。

## 账本与续跑

实验入口为 [`tools/ocr_experiment.py`](../tools/ocr_experiment.py)，命令行仅接收清单和输出目录两个位置参数。它从本机程序的 `QSettings('FormulaOCR', 'Desktop')` 读取 Base URL、模型名称，从系统 keyring 读取 API Key；不需要把密钥写入清单。每个清单项的 `prompt` 才是实际请求所用提示，脚本中的常量不会自动替换清单内容。

所有轮次必须继续使用同一个 `api-ledger.sqlite3`。续跑前停止实验进程，先备份账本，再使用原输出目录，例如在仓库根目录执行：

```powershell
$experimentRoot = "artifacts/improvement-2026-11-18"
$backupStamp = Get-Date -Format "yyyyMMdd-HHmmss"
Copy-Item -LiteralPath "$experimentRoot/api-ledger.sqlite3" -Destination "$experimentRoot/api-ledger.before-resume-$backupStamp.sqlite3"
.venv/Scripts/python.exe tools/ocr_experiment.py "$experimentRoot/regression-manifest.json" "$experimentRoot"
```

上述清单已执行过；原账本存在时，重复运行会跳过已有 `run_key`，不会再次消耗这些请求。其他已保存清单包括 `target-manifest.json`、`font-manifest.json`、`validation-manifest.json` 和 `transport-retry-manifest.json`。需要新一轮时，应审查清单及预算，并在同一账本中使用新的、可追溯的 `run_key`；清单包含本机绝对路径，迁移环境时须先调整输入路径。

预算规则由脚本的 SQLite 事务执行：并发数为 2，每次请求发送前先预留一条账目；成功、失败和中断后残留的 `reserved` 都计入 2000 次上限。已有键无论成功或失败均跳过，脚本不静默重试。中断后先检查账本和返回文件，不能删除原账目再重跑；明确需要的网络补测应使用新键、保留与原请求的对应关系，并额外计费和计数。本轮补测清单使用 `retry_of` 标记对应原请求。

**不要删除、重建账本，也不要换一个输出目录来规避上限。** 上限依赖该账本保存的累计记录；更换目录会产生新的账本，不能被视为原任务预算重新开始。独立验证另用 100 次，至此同一账本共计 650/2000 次。续跑时请以账本实际计数为准。备份用于恢复证据，不用于回滚已经消耗的请求。
